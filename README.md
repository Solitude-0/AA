## 这套系统解决什么问题

| | 现有选股系统（`测试\webapp`） | 本项目（分析看盘） |
|---|---|---|
| 回答的问题 | 买什么——判型、评分、候选、回测 | 现在市场在发生什么——强弱、热点、资金 |
| 时间尺度 | T+1，收盘后批量 15~25 分钟 | T+0，盘中 1~5 秒 |
| 压力来源 | CPU（指标计算） | I/O（上游限流、连接数） |

两者**不合并代码，只共享基础设施**：同一个 PostgreSQL 实例（新库 `realtime`）、同一套代码映射与快照字段知识。

## 三条与需求书不同的判断

### 1. 秒级可行，但天花板是 2~5 秒

腾讯快照全市场 0.22 秒拉完，瓶颈不在我们——在源端。行情时间戳固定落后本机 2~5 秒，**任何架构都消不掉**。体感上"秒级刷新"是真的，但不能用于分钟级以下的抢跑。UI 必须常驻延迟角标。

### 2. 建议砍掉 Redis 与 TimescaleDB

- 单进程单用户场景，内存 `dict` 读取比 Redis 快 3 个数量级，且省掉一个 Windows 上难维护的组件（微软版停更于 3.2，需 Memurai 或 WSL2）。
- TimescaleDB **无 Windows 官方二进制**；PG 原生「按日分区 + BRIN 索引 + 物化视图」等价替代，能力不损失。
- 容量测算：日增约 200 MB，稳态 1.8 GB。

升级判据（三条都不满足就别加）：worker > 1 / 并发客户端 > 50 / 需要多机或对外服务。

### 3. 全市场资金流做不到

东财个股资金流一页 100 条，5563 只需 56 页，且裸请求成功率 0%。必须收敛为 **Top100 排行 + 自选池逐只查询**。

## 架构

```
展示层   Vue3 + Canvas（指数条 / 宽度 / 板块矩阵 / 个股表 / 盘口 / 资金流 / 异动流）
   ↑ WS 按订阅推送（21 KB/帧） + REST 首屏
连接层   WebSocket 订阅 + 合帧 50ms + 慢连接丢弃
   ↑
计算层   宽度聚合 / 涨跌停判定 / 板块排序 / 异动规则（全部增量）
   ↑
热存储   进程内存 dict（5563 行快照 + 1043 板块，覆盖写）—— 替代 Redis
   ↑
采集层   令牌桶 / 域名轮换 / 退避重试 / 熔断 / 交易日闸门
   ↑
持久层   PostgreSQL 17（分钟快照 / 自选 tick / 板块分钟 / 龙虎榜，按日分区滚动）
```

**为什么推送按订阅**：全市场广播 640 KB/帧 ≈ 5 Mbps，浏览器每秒 diff 5343 个对象会卡死；订阅式 21 KB/帧。

## 四条铁律

1. **涨红跌绿**（`--up: #c62828` / `--down: #2e7d32`）。正面定性文字一律不用绿色，避免与"绿=跌"冲突。
2. **东财请求不带 `Referer`**，且必须做域名轮换 + 3 次指数退避（裸请求实测 0/12）。
3. **热数据不进库**。3 秒级快照写 PostgreSQL 是最常见的性能自杀方式；内存留最新，库只存分钟级与收盘。
4. **成交量单位不统一**：腾讯对科创板（688）返回「股」，其余返回「手」。必须用 `[35]` 成交额反推判定，
   且**外盘/内盘要同步归一**，否则内外盘比错 100 倍。这个 bug 是 M0 自检的量级断言抓出来的。
