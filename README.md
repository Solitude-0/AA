# 分析看盘 · Analysis Board

面向个人投资者的 A 股秒级盯盘系统：**指数 → 板块 → 个股 → 盘口 → 资金流 → 异动**，五层钻取。

> **当前状态：M1–M5 全部落地，可日常使用**（2026-10-23）
> 服务：`http://127.0.0.1:8768` ｜ 接口文档：`/api/docs`
> - 全市场 **5343 只 / 稳态 367 ms / 命中 100% / 坏数据 0**
> - 成交额对账：自算 10,557 亿 vs 指数口径 10,680 亿 = **−1.15%**
> - 完整设计：[`docs/分析看盘-完整方案-20261023.html`](docs/分析看盘-完整方案-20261023.html) ｜ 数据源手册：[`docs/数据源手册.md`](docs/数据源手册.md)

| | 分析看盘（本项目） |

## 五条与需求书不同的判断

### 1. 秒级可行，但天花板是 2~5 秒
腾讯快照全市场 0.37 秒拉完，瓶颈不在我们——在源端。行情时间戳固定落后本机 2~5 秒，**任何架构都消不掉**。UI 常驻延迟角标，并且**只在连续竞价时段告警**：午休/盘后源端时间戳本来就不推进，标红只会让你误判系统故障。

### 2. 砍掉 Redis 与 TimescaleDB
- 单进程单用户，内存 `dict` 读取比 Redis 快 3 个数量级，且省掉一个 Windows 上难维护的组件。
- TimescaleDB **无 Windows 官方二进制**；PG 原生「按日分区 + BRIN + COPY」等价替代。实测日增约 200 MB，稳态 1.8 GB。
- 升级判据（三条都不满足就别加）：worker > 1 / 并发客户端 > 50 / 需要多机或对外服务。缓存访问已收敛在 `store.py`，要换只改这一个文件。

### 3. 资金流：东财优先，新浪样本池兜底 ★（14:00 补齐）

东财的 `clist?fid=f62`（个股净额排行）与 `fflow/kline/get`（大盘分钟净额）是**路径级封锁**，
三个镜像域名（`push2` / `1.push2` / `push2delay`）全部 curl(56) 断连。但它**不是永久性的**：
14:00 复测这两条路径突然全通（拿到了全天 240 个分钟点和全市场 Top100），十几分钟后又断——
和板块的 `clist` 是同一个脾气（限时窗口）。因此代码不假设它永久不可用：

| 情形 | 走法 | 口径 |
|---|---|---|
| 东财通 | `fflow/kline` + `clist?fid=f62` | **全市场** Top100 排行 + 全天分钟主力净额 |
| 东财不通 | 新浪 `ssi_ssfx_flzjtj` 逐只查 | **样本池**内排行（成交额前 120 + 自选）+ 池子合计当分钟代理 |

东财失败即记 **15 min 冷却**，到期再探一次，通了自动切回全市场口径（两条口径的分钟点不会拼在同一条曲线上）。

新浪兜底源的字段与边界（实测）：

- 只给**单只个股**的四档主动买卖额（元）：`r0` 超大单 / `r1` 大单 / `r2` 中单 / `r3` 小单，各带 `_in` `_out`；
  主力净额 = `(r0_in-r0_out) + (r1_in-r1_out)`，与接口返回的 `netamount` 逐只对齐过。
- **没有排行榜接口**（`ssl_bkzj_bk` / `ssl_qsfx_zjlrqs` 一律 `Input error`，`ssl_bkzj_zjlrqs` 返回 `[]`），
  所以排行只能自己枚举标的 → 口径天然是「样本池内排序」，页面标题与图例都照实写，不冒充全市场。
- **指数返回 null**（`sh000001` / `sz399001` / `sh000300` 都试过），大盘分钟净额没有真源，
  兜底时用「池子四档合计」当代理，图例标「样本池代理 · 成交额前 N 名」。
- **没有板块净额**：板块榜此时为空，卡片自动从「板块 Top10」切到「个股 Top10」，绝不拿 0 充数。
- 停牌 / 当日无成交（`trade=0, volume=0`）返回 `None`，不返回全 0 行——「没成交」和「没资金进出」是两回事。

成本：120~130 只 × 6 并发 × 12 qps ≈ **9~10 s / 轮**，节拍放到 **60 s**（原本 5 s）。
5 s 一轮等于每秒 24 个请求，既浪费又容易被新浪限流，而资金流本身就是日内累计值，60 s 分辨率足够。
详情抽屉里点开任意个股（池外也算）会**现查一只**，约 40 ms，带 20 s 缓存。

### 4. 东财的封锁是「路径级 + TLS 指纹级」，不是 IP 级 ★（13:30 修正）

上午的结论写的是「东财 IP 级封禁」。下午做 K 线时逐项复测，**这个结论是错的**，真实情况是两层规则叠加：

| 目标 | urllib | 系统 curl | curl_cffi(chrome) | 判定 |
|---|---|---|---|---|
| `www/quote.eastmoney.com` 页面 | 200 | 200 | 200 | 正常 |
| `datacenter-web` 龙虎榜 | 200 | 200 | 200 | 正常 |
| `push2` `ulist.np/get`（批量报价） | 200 | 200 | 200 | 正常 |
| `push2` `stock/get`（单只详情） | ✗ 断连 | 200 | 200 | **TLS 指纹** |
| `push2` `stock/details/get`（逐笔） | ✗ 断连 | 200 | 200 | **TLS 指纹** |
| `push2his` `kline/get`（K 线） | ✗ 断连 | 200 | 200 | **TLS 指纹** |
| `push2` `clist/get`（板块/资金流） | ✗ | ✗ 000 | ✗ 56 | **路径封锁** |
| `push2` `fflow/kline/get`（资金流） | ✗ | ✗ 000 | ✗ 56 | **路径封锁** |

所以：
- **不是 IP 被封**——同 IP 下七八个接口都是 200，换请求头也没用，换 TLS 指纹立刻通。
- 通道因此改成三级引擎：`curl_cffi`（默认，约 40 ms，进程内伪装 Chrome）→ `urllib` → 系统 `curl` 子进程（沙箱里进程启动要 1.3 s，只当最后兜底）。
- 装上 curl_cffi 后**逐笔、单只详情、K 线全部恢复**；仍然挂的只剩 `clist` / `fflow` 两个**路径**——即板块三维与资金流排行。
- 保留原降级设计不变：单类别失败不拖累其他类、渐进冷却 30→300 s、板块保留旧数据并标「旧数据」。
- **这两条路径的封锁是间歇性的**：14:00 复测 `fflow/kline/get` 与 `clist?fid=f62` 曾同时恢复（拿到全天 240 点 + 全市场 Top100），
  十几分钟后又断。所以资金流做成「优先东财 + 15 min 冷却 + 新浪兜底」，不写死成永久不可用。
- 附加收获：`stock/details/get` 与 `clist` 原本共用一个熔断器，板块连续失败会把逐笔一起熔断。已把逐笔拆到独立通道 `_trade`。

**仍待解决**：板块清单的首选来源只有 `clist`（`fs=m:90+t:2/t:3/t:1`），该路径会**间歇性**被断
（13:30 复测时概念/地域能出 516/31 条，几分钟后又全断）。因此已加**新浪兜底源**（`collector/sina.py`）：

| | 东财（首选） | 新浪（兜底） |
|---|---|---|
| 行业 / 概念 / 地域 | 496 / 516 / 31（三级细分） | 49 / 175 / 31（粗分类） |
| 涨跌幅、成交额、领涨股 | ✅ | ✅ |
| 主力净流入 | ✅ | ❌ |
| 成分股涨跌家数 | ✅ | ❌（只有成分股总数） |

调度策略：东财连续失败 3 轮（≈18 s）才切新浪，并冷却 120 s 再试东财——
否则会「东财偶尔成功 → 切回 516 条 → 下一轮又失败」来回抖，板块面板每 6 秒变一次大小。
**「3 轮耐心」只在有旧快照可看时成立**（2026-10-23 16:00 补）：快照为空（刚重启 /
该类别从未成功过）时直接切兜底——收盘后板块节拍降到 600 s，首轮失败还会退到 3600 s，
「等 3 轮」在盘后等于 30 分钟白面板（当天用户截图「板块内容为空」的根因：
15:28 重启后东财封锁，行业/概念两类的兜底一次都没轮到）。东财「200 + 空 diff」
的封锁形态同样按空快照处理。`/api/boards` 的每行带 `src` 字段，前端据此把
「主力净额」「涨跌家数」显示成 `—` 而不是 0.000。
**每类板块内部只会是单一来源**（`store.apply_boards` 整类替换，不做增量合并）。

### 5. 并发数必须实测，不能拍脑袋
全市场 5343 只 = 18 批，实测中位耗时：

| workers | 3 | 4 | 6 | 8 | 12 | 18 |
|---|---|---|---|---|---|---|
| 一轮耗时 | 1065 ms | 479 | 420 | **376** | 372 | 3006~12014（被惩罚） |

8 是拐点。真正的限流器是令牌桶（`qps=20`，容量 ≥ 批数），线程数只决定「一轮 18 批能不能一次发完」。

> 另一个自坑：压测时把 `tracemalloc.start()` 放进每轮计时，把 376 ms 拖成 2.4 s——**工具自己成了瓶颈**。内存现在单独测一轮。

## 选股：两级漏斗（2026-10-23 落地）

全市场 5342 只不可能逐只拉分时。所以拆成两层，**只为 candidates 之外的工程量付代价**：

| 层 | 干什么 | 请求次数 | 实测 |
|---|---|---|---|
| A 快照层 | 用已有的全市场快照字段判定（竞价涨幅、内外盘、是否摸过涨停、价格/市值/换手/成交额） | **0 次额外请求** | 5342 → 4051 |
| B 精筛层 | 只对 A 层候选拉 1 分钟 K 线判形态（平台、回踩、均线金叉、尾盘） | 每种模式各 `per` 只 | 20 只 → 命中 215 |

**按模式分预算是必须的。** 第一版整体按成交额取前 40 去拉分时，结果平台突破 / 均线金叉这类小票形态
全被权重股挤掉——`trunc_modes` 里只剩 `['platform','dragon','ma','tail']` 一直被截。
改成每种 B 层模式各自分预算（`per = max(6, probe // B模式数)`）、各自按本模式特征排序
（gap→竞价涨幅、order→外内比、其余→涨幅）之后，六条路才有均等机会被看见。

**慢的根因在源站，不在代码**：单只 1m 请求实测 **2.9~10.2 s**（`push2his` 间歇性可用）。
所以加了两道闸：整批 `PROBE_TIMEOUT = 10 s` 墙钟上限，超时的部分在面板上用 `timed_out` 明写出来，
而不是悄悄少给几只；以及**精筛专用 60 s 短缓存**（连续筛选时对同一批热门票不再重复拉——
这里是判形态、不是显示 K 线，60 s 只差最后 1~2 根 bar，不影响判定）。
并发从固定 6 改成 `min(16, max(6, 候选数))`：候选本来就不多，多排一轮就是白等 10 s。
改完首次 21.5 s → 9.1 s。

六种模式的判定条件、字段来源、默认参数与「哪些条件判不了」逐条对照在
`docs/选股模式需求.md`。判不了的一律标 `na`（大单扫单笔数、北向资金、机构席位、个股标签），
**不拿近似值冒充**。

**分时源彻底取不到时会明说。** 漏斗行会显示「B 层模式本次全部无法判定」——依据是接口返回的
`probe_ok`（真正拿到分时的只数）。这种时候结果里剩下的命中**全是 A 层**（开盘突破、盘口内外盘），
不是"今天形态票少"。实测 2026-10-23 15:20 之后正是这个状态：`kline` 通道 17 次请求 0 成功，
`probed=12 probe_ok=0 total=214` —— 214 条全是 A 层，一个数都没瞒。

### B 层离线单测（为什么要脱离源站）

四个形态模式（平台突破 / 龙回头 / 金叉 / 尾盘）靠 1m 分时判定，而 `push2his` 是间歇性可用的。
靠线上偶遇来验证，等于把「逻辑对不对」押在运气上——大多数时间这条路径根本没被执行，错了也看不见。
所以 `tools/pick_rules_test.py` 直接手工造分时序列打进 `_judge_b`，**跟源站好不好完全无关**：

```
.venv\Scripts\python.exe tools/pick_rules_test.py    # 15 项断言：平台 5 / 龙回头 4 / 金叉 2 / 尾盘 3 / 无数据 4
```

写这组测试时量出两件事，都记在这里免得下次重蹈：

1. **「分时均线金叉」比听上去严格得多。** 它要求 `红柱放大`（`hist[-1] > 0 且 ≥ hist[-2]`）。
   这不是 bug——等速上涨时 DIF 增速递减，MACD 柱本来就会先放大后收敛，
   **股价还在涨、但柱已经开始缩短的那一刻会被判否**。造正例测试用例必须给加速度。
   实盘含义：这个模式挑的是"动量仍在增强"的票，等速爬升的老牛股会被刷掉。

2. **`tail` 模式里那条「尾盘破位」是死代码（待决）。**
   条件是 `现价 < 14:30 之后所有 bar 的最低价`，而 `after ≥ 3%` 又要求
   `现价 ≥ 锚点收盘价 × 1.03 ≥ 锚点最低价`，锚点那根的最低价也在 `low_after` 里 ——
   **两条约束数学上互斥，这条分支永远进不去。** 它不会误伤任何人，
   但会让人以为"尾盘有破位保护"，属于看着有检查其实没有。
   待你定：是删掉、还是把 `low_after` 改成「最后 N 根的最低价」让它真正生效
   （后者语义更准：尾盘拉起来又跌回去才算破位，代价是判定变严）。

## K 线：缩放与压力支撑

| 操作 | 行为 |
|---|---|
| 滚轮 | 以**光标位置为锚点**缩放——放大后鼠标底下那一根还在原处，不会跑掉 |
| 拖拽 | 向右拖 = 看更早的一段，拖到两端自动夹紧 |
| 双击 / 「复位」 | 回到默认视角（日/周/月 120 根，分钟线 160 根） |
| ＋ / － / 全览 | 按钮式缩放，`kOff` 归零贴回最新一段，与滚轮的锚点缩放互补 |

**压力支撑怎么算的**（只说方法，不给预测）：

```
摆动点   左右各 2 根都不超过它  →  局部高点 / 局部低点
聚类     0.6% 以内算同一价位    →  "一个价位"而不是"一根 K 线"
打分     触碰次数 × 10 + 最近性 × 6
取值     现价上方第 1~3 名 → R1/R2/R3（橙，虚线）
         现价下方第 1~3 名 → S1/S2/S3（蓝，虚线）
筹码     成交量按价格分 30 箱，占比前 2 且 > 6% 才画（半透明蓝带）
```

三条必须说清的边界：

1. **只用当前可见区间算。** 能看到多少根就按多少根算，跟手动画线的习惯一致；缩小视野会自然长出更多级别。
2. **均线在完整序列上递推**，否则可见段最左边那几根没有 MA5/MA10。
3. 这条线只是在陈述「这些价位被反复试探过」，**它不是预测。** 触碰次数多不等于撑得住，
   破位往往恰恰发生在被多次试探之后。

真实数据自检（`tools/kzoom_check.js --real=600519`，12 项断言全绿）：
贵州茅台 320 根日线、现价 1329 → 压力 1343.30（4 次）/ 1360.97（3 次），
支撑 1281.97（3 次）/ 1266.67（2 次）/ 1224.12（3 次），筹码密集 1259.44、1299.61 各约 9%。

## 四条铁律

1. **涨红跌绿**（`--up` 红 / `--down` 绿）。正面定性文字一律不用绿色，避免与「绿 = 跌」冲突；格式化必须把 `-0.00` 归一成 `0.00`。
2. **热数据不进库**。3 秒级快照写 PostgreSQL 是最常见的性能自杀方式；内存留最新，库只存分钟级与收盘。
3. **成交量单位不统一**：腾讯对科创板（688）返回「股」，其余「手」。用 `[35]` 成交额反推判定，且**外盘/内盘要同步归一**，否则内外盘比错 100 倍。
4. **指数不是个股**：指数的「现价」是点位，`成交额 ÷ 量 ÷ 点位` 恒等于 0.42 左右，用个股的量价断言会把 5/7 条指数当坏数据丢掉。判定见 `tx.is_index_sym()`。
