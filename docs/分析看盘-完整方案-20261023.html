00一页结论与需求判定

先给判断，再讲理由。这套系统能做，而且比需求书写的更省钱——但需求里有两处口径必须改，否则会做出一个"指标齐全但数字不可信"的系统。

结论一 · 秒级可行
全市场 0.22 秒一轮
腾讯快照 5343 只 / 18 批 / 8 并发实测 367 ms（p95 396），命中率 100%。瓶颈不在我们，在源端：连续竞价时段行情时间戳落后 2~5 秒，这是免费源的天花板，任何架构都消不掉。
结论二 · 砍掉 Redis 与时序库
省 2 个组件，0 损失
单进程单用户，内存 dict 就是最快的 Redis；PG 原生月分区替代 TimescaleDB（后者无 Windows 二进制）。写入约 200 MB/天，PG 毫无压力。
结论三 · 全市场资金流做不到
只做 Top 榜 + 自选池
东财个股资金流一页 100 条，5563 只需 56 页；且裸请求成功率 0/12。全覆盖按秒刷新不成立，必须收敛到「Top100 排行 + 自选池逐只」。
一句话架构 腾讯快照扛全市场（价格/五档/内外盘/涨跌停判定）→ 东财补板块与资金流（重试+熔断）→ 单进程内存做热层 → PostgreSQL 只存分钟级与收盘 → WebSocket 按订阅推送，不广播全市场。

Redis 缓存Redis + 时序库，毫秒级读取建议取消Windows 下 Redis 无官方维护版（微软版本停更于 3.2），需 Memurai 商业版或 WSL2。单进程内存读取比 Redis 快 3 个数量级。
WebSocket 推送秒级推送，避免轮询延迟原样可做但必须按订阅推送：全市场 5343 只一秒一推 = 640 KB/帧 ≈ 5 Mbps，浏览器每秒 diff 五千对象会卡死。
目标用户散户 / 分析师 / 机构交易员需收敛本方案按单机单人自用设计（瓶颈是数据源，不是并发）。「机构交易员盘口」需 L2 十档与委托队列，属付费范畴。
最需要你知道的一件事 免费行情源的延迟是 2~5 秒（两次实测：2~3 s 与 5.4 s，随盘中波动）。体感上"秒级刷新"是真的，但不能用于分钟级以下的抢跑——你看到的价格已经是几秒前的市场。所有 UI 必须常驻「行情延迟」角标，这是诚实，也是防止自己被自己骗。

01项目定位与系统边界

本项目独立立项、独立部署、零外部依赖：不读任何其它本地项目的产物、不调它们的接口、不复它们的代码。代码清单自带（data/codes.json）、数据库用独立库 realtime、前端与绘制全部自研。删掉 E 盘上任何其它项目，本系统照常跑。

维度分析看盘（本项目）
回答的问题"现在市场在发生什么"——强弱、热点、资金
时间尺度T+0，盘中 1~5 秒
数据形态内存热快照 + 分钟级落库
压力来源I/O（上游限流、连接数）
依赖边界零代码依赖、零接口依赖。唯一共用的是本机 PostgreSQL 实例（独立库 realtime，删别的库不影响本系统）。所有代码清单、映射规则、绘制组件都在本仓库内。
为什么必须单进程单 worker 热快照、订阅集、异动缓冲全部在进程内，多 worker 会各持一份，推送立刻错乱。若把秒级推送和任何批量计算塞进同一进程，一次大计算就会把 WebSocket 连接全部拖死。物理隔离是成本最低的稳定性方案——两个进程抢 CPU 最多是慢，抢事件循环是直接挂。

3.2 为什么推送必须「按订阅」

推送策略单帧大小1 Hz 带宽前端压力判定
全市场广播≈ 640 KB≈ 5 Mbps每秒创建并 diff 5343 个对象，表格卡顿不可行
订阅式（指数 7 + 板块 20 + 可见 100 + 自选 50）≈ 21 KB≈ 170 kbps只更新 177 个对象采用

REST 负责首屏全量（进入页面一次），WebSocket 只负责增量。翻页时发一次 REST 拿新页 + 改订阅集，之后靠 WS 增量。

3.3 为什么不用 Redis

Redis 的作用本场景是否需要替代方案
跨进程共享缓存不需要 单进程单 worker模块级 dict，读取 ~100 ns
高速读写（10 万 QPS）不需要 实际负载 <20 QPS同上
Pub/Sub 广播不需要 单进程内直接遍历连接asyncio.Queue per connection
持久化不需要 落库走 PGPG 分区表
Windows 可维护性负分 微软版停更、Memurai 商业版 / WSL2省掉
什么条件下必须回头上 Redis（判据，别拍脑袋） ① uvicorn worker 数 > 1（多进程需共享快照）；② 同时在线客户端 > 50（连接状态跨进程）；③ 需要多机部署或对外服务。 只要三条都不满足，加 Redis 就是纯负担。代码预留抽象：所有缓存访问走 store.py 的 get/set/subscribe 三个函数，将来替换只改这一个文件。

4.3 通道实现骨架

class Channel:
    """带令牌桶 / 域名轮换 / 退避重试 / 熔断的 HTTP 通道"""
    def __init__(self, hosts, qps=10, timeout=6, breaker=5):
        self.hosts, self.timeout = hosts, timeout
        self.bucket, self.breaker = TokenBucket(qps), breaker
        self.fails, self.open_until = 0, 0.0

    async def get(self, path, tries=3):
        if time() < self.open_until:
            raise CircuitOpen                 # 上层直接用缓存
        await self.bucket.take()
        for i in range(tries):
            host = self.hosts[i % len(self.hosts)]   # 每次重试换域名
            try:
                r = await fetch(f"https://{host}{path}", headers=UA_ONLY)
                self.fails = 0
                return r
            except Exception:
                await sleep(0.25 * 2**i + random() * 0.15)
        self.fails += 1
        if self.fails >= self.breaker:
            self.open_until = time() + 60            # 熔断 60 s
        raise AllHostsFailed

4.4 解析器必须自校验

腾讯接口无字段名，全靠位置索引，且不同标的字段数不同（个股 88、北证50 87）。历史上出现过字段错位，表现为"某个指数涨跌幅永远是 0"，极难排查。

# 第 0 步：先归一成交量单位（关键，见下方警告）
amt_yuan = _f(f[35].split("/")[2])      # [35]="价/量/成交额(元)"
ratio = (amt_yuan / vol_raw) / price
share_per_unit = 1 if 0.5 < ratio < 2.0 else 100   # ≈1→股，≈100→手
vol_hand = vol_raw * share_per_unit / 100

# 三重断言
assert abs(price - prev - chg) < 0.02                          # 字段错位
assert abs(pct) <= 31                                          # 涨跌幅越界
assert 0.5 < (amt_yuan / vol_raw) / (price * share_per_unit) < 2.0   # 单位/量级不符

校验不过的行直接丢弃并计数，不进入 UI。单轮失败率 > 0.5% 触发告警（说明源在改格式）。

★ 成交量单位不一致：科创板是「股」，其余是「手」 这是 M0 自检时被量级断言抓出来的真 bug——605 条坏数据全部来自 688 开头。
sh688001：[6]=8666261，× 40.22 ≈ 3.49 亿 ≈ 成交额 3.53 亿 → 股
sh600519：[6]=35148，× 100 × 1339 ≈ 470 亿 ≈ 成交额 467 亿 → 手
判定方法（不要按代码前缀硬编码）：用 [35] 的成交额反推 ratio = (成交额 ÷ 量) ÷ 现价，≈1 判为股、≈100 判为手，统一归一到「手」。
连带坑：外盘 [7]／内盘 [8] 与 [6] 同单位，必须同步归一， 否则内外盘比会错 100 倍——而内外盘比恰好是盘口模块的核心指标，错了整块数据都是废的。
三个必须遵守的细节（都是实测踩出来的） ① 请求头只给 User-Agent，绝对不要带 Referer——带上就被 WAF 断连（两次复测均 FAIL）。
② 不要用全局 semaphore 代替令牌桶。信号量只限并发不限速率，18 批瞬间打完照样触发限流。
③ 腾讯返回 GBK，必须显式 decode('gbk')；用 utf-8 得到的是乱码名称而不是报错，属于静默错误。

5.2 板块聚合与排序

# 板块列表直接取东财已聚合好的字段（不自己算，省 CPU 且口径一致）
pct     = f3      # 板块涨跌幅（东财按流通市值加权）

# 排序键（服务端做，前端不排）
sort_key = {
  "pct":  lambda b: b.pct,
  "amt":  lambda b: b.amt,
  "net":  lambda b: b.net_in,
  "heat": lambda b: b.pct * 0.6 + (b.net_in / max(b.amt, 1)) * 1e6 * 0.4,  # 热度综合
}

「热度」是我加的复合排序：单纯按涨幅排会全是小盘妖股，单纯按净流入排会全是大盘蓝筹。涨幅为主、资金强度（净流入/成交额）为辅，能同时压掉这两类噪声。系数可调，但两个量都要先做截面归一化。

5.4 异动规则（三条，全部可实时算）

6.3 容量测算（决定要不要上时序库）

表日增行数单行估算日增体积保留稳态
snap_min（全市场每分钟）240 × 5563 = 133 万~90 B~120 MB5 天600 MB
tick_sec（自选 200 只 / 5 s）2880 × 200 = 57.6 万~80 B~46 MB20 天920 MB

合计215 万~196 MB≈ 1.8 GB

日增约 200 MB、稳态 1.8 GB、查询只有两种形态（"某时刻全市场"和"某只最近 N 分钟"）——PostgreSQL 完全够用，且已有现成实例。TimescaleDB 的压缩和连续聚合在这里省不了多少空间，但会带来 Docker/WSL 的运维负担——Windows 上没有官方二进制，这是硬约束。

如果坚持要「时序库」这个名分 用 PG 原生能力等价实现：声明式分区（按日）+ BRIN 索引（时间列天然有序，索引体积约为 B-tree 的 1/100）+ 连续聚合用物化视图（每分钟 REFRESH MATERIALIZED VIEW）。 这三件套就是 TimescaleDB 的核心功能，PG 内置。结论：不上 TimescaleDB，能力不损失。

WS 的价值不是"比轮询快"，而是服务端能做聚合、去重、增量、顺序保证。设计不当会比轮询更糟。

7.3 三条硬规则

合帧 50 ms
不同采集任务在同一 50 ms 窗口的变化合并成一帧。否则 1 秒内 4~5 个小帧，前端触发 4~5 次重渲染。
断线必全量
重连后先发 full:true 全量帧再回增量。只发增量会因中间漏帧导致价格永远停在旧值——最难查的一类 bug。
慢连接丢弃
每连接一个 Queue(maxsize=50)，满则丢最旧帧。宁可缺一帧，也不能让卡住的浏览器拖慢整个事件循环。

7.4 为什么保留 REST

  • 首屏：一次拉当前状态，比等 WS 逐帧推送快且逻辑简单
  • 翻页 / 排序 / 筛选：服务端持有全量快照，一次返回 50 行，比让前端持有 5343 行更省内存
  • 降级：WS 建连失败（企业代理、防火墙）自动回落 3 s 轮询，功能不中断
  • 可调试：curl 能验证的东西，永远比只能开浏览器验证的东西好维护

9.4 三个防坑设计

  • 延迟角标：顶栏常驻「行情延迟 3.2s」并同时显示时段标签。交易时段按 <3s / 3~5s / >5s 三档着色；午休与盘后显示「已收盘 / 价格冻结」而非告警——因为此时源端时间戳本来就不推进，标红只会让自己误判系统出故障。数据陈旧（熔断复用缓存）时表格整体降透明度。

  • 订阅跟随视口：翻页/筛选后立即 unsub 旧代码、sub 新代码。不跟随会导致订阅集无限膨胀，几分钟后被慢连接保护踢掉。

D. 口径约定（写进代码注释，避免半年后自己看不懂）
